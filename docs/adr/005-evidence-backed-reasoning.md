# ADR 005: Evidence-Backed Reasoning

## Status

Accepted

## Date

2024-01-01

---

## Context

Professor v10 uses automated analysis to produce architectural recommendations. In an enterprise context, developers and architects must be able to **trust** the output. The core trust problem with AI-based or automated reasoning systems is:

- They can produce plausible-sounding but incorrect claims
- They can miss dependencies that were not in the analyzed scope
- Their confidence in incorrect claims is indistinguishable from confidence in correct claims
- Enterprise decisions made on faulty architectural output lead to production incidents

The question is: how do we make the system's outputs trustworthy enough for enterprise architectural decisions?

---

## Decision

**All AI-generated and automated recommendations must cite source code evidence. No claim may appear in output documents without a traceable source. Confidence scoring is required for all claims.**

### Three-Part Evidence Requirement

Every claim in the output must satisfy three requirements:

#### 1. Source Traceability
Every claim must link to:
- Repository name
- File path
- Line number
- (Optional) Git commit SHA for point-in-time reproducibility

**Example**: "feed-service calls coupon-engine"
- Evidence: `feed-service/src/main/java/clients/CouponEngineClient.java:23`
- Detection: `@FeignClient(name = "coupon-engine")`

#### 2. Confidence Score
Every claim receives a numeric confidence score (0.0–1.0):

```python
class Claim:
    statement: str
    evidence_links: list[SourceLocation]
    confidence: float  # 0.0 to 1.0
    detection_method: str  # "annotation", "naming_convention", "import_analysis", etc.
    requires_review: bool  # True if confidence < threshold
```

#### 3. Review Flagging
Claims below the confidence threshold (default: 0.60) must be **explicitly flagged** in the output document as requiring human verification. They are not presented as facts.

### Output Document Contract

An architectural document generated by Professor v10 must include:
1. A **Trust Summary** section with overall confidence score and count of review-required claims
2. Evidence footnotes on all service/dependency/contract claims
3. An explicit **Parsing Scope** statement listing which repos were analyzed
4. An **Out of Scope** warning for repos not analyzed

---

## Consequences

### Positive
- Engineers can verify every claim against source code
- Low-confidence claims are surfaced for human review rather than silently included
- Trust summary gives architects a quick quality signal on the output
- Reproducible: given the same code at the same commit, output is deterministic
- Builds institutional trust in the system over time as claims are verified

### Negative
- Adds complexity to the output document structure
- Requires every parser to carry source location metadata through to the graph
- May surface many "review required" flags initially — noise until parsers improve
- Confidence calibration requires empirical tuning

### Non-Negotiable Rules

These rules are enforced in `src/validators/evidence.py` and cannot be disabled:

| Rule | Description |
|---|---|
| R1 | Every graph edge must have a source location |
| R2 | Every impact report finding must have an evidence link |
| R3 | Output documents must include a Trust Summary section |
| R4 | Claims below 0.60 confidence must be marked as REVIEW REQUIRED |
| R5 | Out-of-scope repos must be disclosed in the output |
